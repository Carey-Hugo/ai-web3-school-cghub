## 一句话理解

> RAG = Retrieval-Augmented Generation（检索增强生成）
> 核心：先从外部知识库找到相关片段，再让 LLM 基于这些片段生成答案。

**解决的问题：**
- LLM 知识过时（训练数据有截止日期）
- LLM 知识不足（垂直领域没有）
- LLM 幻觉（编造不存在的内容）

---

## 工作流程（四步）

```
用户问题
  ↓
① 检索（Retriever）：从 Vector DB 里找最相关的知识片段
  ↓
② 合并：将检索结果 + 用户问题一起注入 Context
  ↓
③ 生成（Generation）：LLM 基于检索结果回答
  ↓
④ 输出：带溯源的回答
```

---

## 四个关键技术

### 1. Chunking（分块）
- 把长文档切成小块（每块 500-1000 token）
- 太长：检索精度下降；太短：丢失上下文
- 策略：按段落、按句子、滑动窗口

### 2. Vector DB（向量数据库）
- 每个 chunk 转成向量（embedding）
- 相似的文本 → 相似的向量 → 一搜就找到
- 工具：Pinecone、Milvus、Chroma、FAISS

### 3. Retriever（检索器）
- 负责根据用户问题找相关 chunks
- 方式：纯向量相似度 / 关键词 BM25 / 混合

### 4. Rerank（重排序）
- 初步检索 → 可能找到 20 条
- Rerank 模型 → 重新排序，选最相关的 3-5 条
- 作用：提高答案质量，减少无关信息干扰

---

## RAG vs 上下文窗口

| | 直接塞进 Context | RAG |
|--|------|------|
| 知识量 | 受 token 上限限制 | 可接入无限知识库 |
| 时效性 | 依赖模型训练数据 | 可实时更新外部数据 |
| 幻觉 | 仍有（模型自己编） | 降低（基于真实文档） |
| 速度 | 快 | 慢（多了检索步骤） |

## CGHub 应用场景

- 公众号历史文章 → 向量库 → 智能问答
- 项目文档 → RAG → Agent 查阅上下文
- 白皮书素材 → RAG → 书籍写作辅助
